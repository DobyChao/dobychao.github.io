Weekly Build #001: SimpleSavePage — 一个把网页存成单文件的小工具

Weekly Build — 一个亿周更新一次的开发日记

起因很简单：我想把一些网页完整保存下来，不是那种"另存为"然后丢给你一堆文件和文件夹的方式，而是一个干干净净的单个 HTML 文件，图片、CSS、字体全塞进去，打开就能看。

找了一圈现成工具，Chrome 的"另存为"会拆出一堆资源文件，SingleFile 扩展倒是不错但不能自己部署，网上的一些方案要么太重要么太简陋。

不如自己搞一个吧。基本上是 vibe coding 出来的 — 跟 AI 聊需求，它写代码，我跑一下看效果，不行就再聊。

Commit 1: 万事开头难，但不难

a8a53db Initial commit: SimpleSavePage - web page downloader with headless Chrome

第一版，能跑就行。Express 后端 + Puppeteer 操控 headless Chrome，前端一个输入框一个按钮。输入 URL → 点 Save Page → 后端开 Chrome 去抓页面 → 把所有资源内联成 data URI → 返回一个自包含的 HTML 文件。

核心保存引擎直接用了 nodeSavePageWE，它本身是从 Save Page WE 浏览器扩展移植过来的，4500 行的 client.js 负责遍历页面所有 frame，收集图片、CSS、字体、脚本等各种资源，然后全部塞成 data URI。

能用了，但问题马上就来了。

Commit 2-3: 等一下…再等一下…

10049a9 Wait for navigation to stabilize before scraping, handle redirect chains like login pages
da49a81 Increase navigation stabilization threshold to 8s for slower login flows

第一版有个很头疼的问题：有些页面会跳转，特别是那种需要登录的页面 — 你输入一个 URL，它先跳登录页，登录完了再跳回目标页面。如果 Chrome 还没跳完就开始抓，抓到的就是登录页而不是目标页。

于是我加了一个"导航稳定检测"的逻辑：等 URL 不再变化了才开始抓取。一开始设了个比较短的时间，结果发现有些网站的登录跳转链特别长，8 秒都不够用。于是又改成了 8 秒。

这就是 vibe coding 的典型节奏：先让它跑 → 发现问题 → 告诉 AI → 它改 → 再跑 → 再发现新问题。

Commit 4: 减法比加法难

d33c97b Remove server-side task history, only show current task progress inline

一开始我在服务端做了个任务历史列表，想着可以回看之前保存了什么。后来发现问题 — 服务端的历史是所有用户共享的，A 用户能看到 B 用户下载过什么，这不合适。每个用户只能看到自己的，那就别在服务端记了。

砍掉了服务端的历史记录，只保留当前任务的实时进度展示。界面清爽了，隐私问题也解决了。

Commit 5-6: 该记的还是得记

82b1e3b Add client-side download history stored in localStorage
05e6b49 Unify download and remove button sizes

服务端不记了，但用户还是需要知道自己之前保存过什么。于是改成了用 localStorage 在浏览器端存历史记录 — URL、文件名、大小、时间，最多记 100 条。

然后发现下载按钮和删除按钮大小不一致，看着别扭，统一了一下。这种小细节就是你自己用的时候才会注意到的。

Commit 7-9: 给自己上锁

9a78127 Move navStableSeconds and access control to server-side config.json only
524bf73 Support regex/full-URL matching in access control, add config docs to README
335aea3 Whitelist overrides blacklist when both lists have values
7c27136 Security: fix path traversal, add final URL re-validation and HTML sanitization

这几条 commit 是我自己要求加的。关键问题在于：这个工具是用服务端浏览器的权限去访问页面的，不是客户端浏览器的权限。这意味着如果有人拿它去访问内网地址，或者构造恶意 URL，后果会很严重。

先是把配置项从代码里抽出来放到了 config.json，不用改代码就能调参数。然后加了访问控制（URL 黑白名单），支持正则、通配符、精确匹配三种模式。白名单总是优先于黑名单 — “即使上了黑名单，只要在白名单里就放行”，灵活度最高。

安全加固：

  • SSRF 防护：禁止通过服务去访问内网地址。不只是检查初始 URL，页面跳转后的最终 URL 也会再验证一遍 — 防止"先跳正常 URL，再 302 到内网"的绕过
  • 路径穿越防护：../../etc/passwd 这种套路拦住
  • HTML 净化：保存下来的 HTML 会去掉 meta refresh、javascript: URL、内联事件处理器等危险内容

技术栈

简单到没什么好说的：

  • Node.js + Express 做后端
  • Puppeteer 操控 Chrome
  • 前端就是原生 HTML/CSS/JS，没上框架
  • 整个项目就几个文件

最满意的功能

复用浏览器环境 — 如果你本地的 Chrome 开了远程调试端口（--remote-debugging-port=9222），SimpleSavePage 会直接连上去，复用你的 cookies、登录状态、权限。需要登录才能看的页面，你在 Chrome 里登了，它就能直接保存。

这才是真正解决痛点的功能。

用法

打开 http://localhost:3000，输入 URL，点 Save Page，完事。

感想

其实这么多 commit 并不是我一个个手动提交的 — AI 每改完一个功能就自己 commit + push 了，所以看起来像是一个很规范的迭代过程，其实每一步都是我跟 AI 对话催出来的。

说回这个项目，它现在已经是太监状态了。核心问题还是那个：服务端浏览器的权限太大了。即使加了 SSRF 防护、黑白名单、HTML 净化，本质上用户可以通过这个工具以服务端的身份去访问任意页面，这个攻击面太大了。如果部署在公网上，等于开了一个代理。后续如果要继续做，得想一个更安全的架构 — 但想了想，投入产出比不高，不如直接用 SingleFile 扩展。

Vibe coding 的体验还是不错的，快速出原型、快速迭代，但安全这类边界情况还是得自己心里有数。AI 能帮你实现，但判断该不该做、做了安不安全，还是得人来把关。
